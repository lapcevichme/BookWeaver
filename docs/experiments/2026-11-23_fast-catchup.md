# Эксперимент: Быстрый режим до закладки (`fast-catchup`)

**Дата:** 2026-11-23
**Ветка:** `feat/fast-catchup`
**Модель:** `deepseek/deepseek-v4.1-flash-1017` (OpenRouter / DeepInfra fp8)
**Эталон:** `kusuriya_117` (4 тома, 104 сюжетные главы, ~265 164 слов)

## 1. Цель
Проверить двухфазную схему (`fast-catchup` для глав `1..K` -> штатный поглавный `CharacterAnalysisPipeline` для `K+1..N`):
- уложиться в бюджет **\$1–\$3** на ~2000 глав (~2.3 млн слов);
- сохранить высокий recall по `protagonist` и `major`, отсеивая одноразовую массовку;
- проверить `reasoning: "low"` vs `reasoning: "none"`;
- проверить стыковку с Фазой 2 и поведение на сложных многотомных арках (переход титула, скрытые личности).

## 3. Выявленные проблемы и принятые решения
1. **Титулы в `name` при `reasoning: "none"`:** в 4-томном прогоне возник дубль из-за добавления титула к имени в одном из батчей. В промпт добавлено универсальное жанрово-независимое правило: в `name` писать только чистое личное имя без титулов/званий/должностей (титул -> `status`-факт).
2. **Персистентность промежуточных `batch_recap`:** сохраняются в `Book.config["catchup_recaps"]` и очищаются после сборки `VolumeSummaryRecord`, чтобы resume посередине тома не терял контекст.
3. **Пометка источника фактов:** все факты Фазы 1 помечаются `"source": "catchup"`.
4. **Проблема `identity_judge` vs `logprobs` (`identity_score`):** занесена в `docs/backlog.md` (#24) как отдельная задача по `pipelines/identity_links.py`.
5. **Книги без деления на тома (арки по главам):** занесена в `docs/backlog.md` (#23).
